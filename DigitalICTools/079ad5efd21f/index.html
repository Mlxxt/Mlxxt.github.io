数字IC课设工具链（三） | 目录、文件和运行位置

发表于2026-06-03|DigitalICTools
|总字数:2.2k|阅读时长:7分钟|浏览量:

第一次跑完整套流程时，我最容易混乱的不是某一个工具命令，而是“这个文件现在应该放在哪里”“这个脚本应该从哪个目录运行”“上一阶段的哪个输出要交给下一阶段”。这篇文章不采用某个固定模板目录名，而是从通用工具链角度整理文件组织原则。

目录名不是重点，文件关系才是重点

不同教学、实验室和公司项目会采用不同的目录结构。工具链本身通常不强制目录必须叫什么名字，它真正要求的是：

  1. 每个工具能找到它需要的输入文件。
  2. 每个阶段的输出能被下一阶段正确引用。
  3. 同名文件不会混淆，例如前仿 SDF 和后仿 SDF 要分开。
  4. 脚本中的相对路径和实际目录一致。
  5. 工艺库、标准单元库、rule deck、映射文件和 corner 设置保持一致。

因此，一个通用项目可以按“阶段”和“文件角色”组织，而不是绑定某一种编号目录。

这种结构的思路是：

区域 放什么 为什么这样分
rtl 设计源码 源码是所有前端流程的根
tb testbench 和验证模型 三次仿真尽量复用同一套功能检查
constraints SDC、MMMC 相关约束 便于跟踪约束版本
scripts 各工具运行脚本 脚本和工具输出分离，方便复现
work 各阶段运行目录 隔离中间产物，避免文件混用
reports 汇总后的关键报告 便于写报告和比较版本
deliverables 最终网表、GDS、SDF、报告包 交付物和临时文件分开

如果项目使用了既有模板，就不一定要改成这个样子；真正重要的是理解每类文件在流程中的角色。

文件流转总表

来源阶段 文件 去向 用途
RTL 编写 RTL .v/.sv VCS、DC、Formality 行为仿真和综合输入
testbench tb .v/.sv 三次 VCS 仿真 产生激励、自动比对、dump 波形
约束编写 .sdc DC、Innovus、PrimeTime 描述时钟、输入输出延时和时序例外
DC 门级 .v Formality、前仿、Innovus 综合后的逻辑网表
DC .sdf 前仿 综合后标准单元延时反标
DC .svf Formality 帮助综合前后等价匹配
Innovus 后端 .v Formality、PrimeTime、后仿、LVS 物理实现后的门级网表
Innovus .gds Virtuoso/Calibre 版图导入和物理验证
Innovus .def StarRC 描述布局布线物理信息
StarRC .spef PrimeTime 后端寄生 RC 参数
PrimeTime .sdf 后仿 最终时序反标

我在整理文件时会特别注意文件版本。比如 .sdf 至少有两类：DC 输出的 SDF 用于前仿，PrimeTime 输出的 SDF 用于后仿。它们不能混用。

各阶段运行位置的通用原则

阶段 运行位置建议 核心原则
RTL 仿真 独立的行为仿真工作区 能找到 RTL、testbench、filelist 和波形输出位置
DC 综合 独立的综合工作区 输入 RTL 和 SDC，输出网表、SDF、SVF 和报告
前端 Formality 独立的形式验证工作区 reference 是 RTL，implementation 是 DC 网表
前仿 独立的门级前仿工作区 使用 DC 网表、DC SDF 和标准单元模型
Innovus APR 独立的后端实现工作区 输入 DC 网表、SDC、LEF、MMMC，输出后端网表、DEF、GDS
Calibre DRC/LVS 独立的物理验证工作区 保存 runset、DRC/LVS 报告和对应输入版本
后端 Formality 独立的后端等价验证工作区 reference 是 DC 网表，implementation 是 Innovus 网表
StarRC 独立的寄生提取工作区 按 corner 输出 SPEF，避免覆盖
PrimeTime 独立的静态时序工作区 输入后端网表、SDC、SPEF 和时序库，输出报告和后仿 SDF
后仿 独立的版图后仿工作区 使用后端网表、PrimeTime SDF 和同一套功能检查逻辑

这里的“独立”不是指一定要新建某个固定名字的文件夹，而是指不要把不同阶段的同名产物混在一起。前仿和后仿尤其要分开，因为它们都会用到网表、SDF、标准单元模型和 testbench，但文件来源完全不同。

RTL 仿真文件清单

文件 作用 容易错的地方
RTL 源码 设计实现 文件没加入 filelist，或者顶层模块名和规格不一致
testbench 功能验证 latency 没对齐，reset 场景覆盖不完整
filelist VCS 编译文件列表 路径写错，依赖顺序错误
Makefile 或脚本 固定仿真命令 变量路径和实际目录不一致
波形文件 Verdi 调试 dump 范围太小，debug 时看不到内部信号

DC 综合文件清单

文件 作用 修改重点
环境脚本 设置库路径和工具环境 保证工艺库和标准单元库版本正确
设计定义脚本 指定顶层和 RTL 文件 必须按当前设计修改
SDC 时序约束 必须按时钟、输入输出延时、reset 语义和接口要求修改
dont use 脚本 限制不用某些标准单元 可按时序、功耗或面积需求调整
综合主脚本 执行 read、elaborate、link、compile、report、write 初学时少改流程，多改输入和约束

DC 输出里最重要的几个文件：

输出 后续用途
综合后门级网表 前仿、Formality、Innovus 的主要输入
DC SDF 综合后门级前仿
SDC 后端继续使用或作为后端约束基础
SVF Formality 前端验证
area/power/timing/QoR 报告 PPA 和优化依据

Innovus 文件清单

文件或区域 放什么 注意
后端输入 DC 网表、SDC、MMMC 这是 APR 的逻辑和约束起点
物理库 LEF、antenna LEF 等 要与工艺和标准单元库匹配
映射文件 stream out map、layer map 等 影响 GDS 导出和后续验证
工作数据库 Innovus 保存的设计状态 便于中断后恢复和重跑
后端输出 后端网表、DEF、GDS、报告 后续所有后端验证都从这里取文件

Innovus 的图形操作会生成命令记录，这是很有用的。第一次可以跟着 GUI 做，第二次就应该开始把稳定操作整理成脚本，否则每次调整 floorplan 都要重新手点，既慢又容易漏步骤。

Calibre 和 Virtuoso 文件清单

项目 需要确认
Verilog import 后端网表导入到正确 library，reference libraries 正确
Stream import GDS 导入到正确 top cell，映射文件和参考库正确
VDD/VSS label 名称、大小写、感叹号、金属层都要和流程一致
DRC runset 使用对应工艺的 DRC rule deck
LVS runset 使用对应工艺的 LVS rule deck、网表、layout 和库

这里最不自由的是工艺相关文件，不能随便换。比较自由的是 runset 保存位置和报告命名，但要能追溯到对应的 GDS、网表和 rule deck。

StarRC、PrimeTime 和后仿文件清单

阶段 文件 注意
StarRC SPEF 不同 PVT corner 要分清
PrimeTime analysis coverage、constraint report、timing report 先看 coverage，再看 slack
PrimeTime SDF 后仿使用的是这里的 SDF
后仿 后端网表、PrimeTime SDF、标准单元模型、testbench 和前仿工作区隔离，避免拿错文件

后仿中最重要的是确认 $sdf_annotate 指向 PrimeTime 输出的 SDF，并且实例名和后端网表层级能对应。

文件归档建议

在进行整理和交付时，文件可以如此整理：

类别 建议保留
源码 RTL、testbench、filelist、仿真脚本
约束和脚本 SDC、DC Tcl、Innovus Tcl/CMD、PrimeTime Tcl
综合结果 DC 网表、SDF、SVF、area/power/timing/QoR 报告
仿真结果 三次 VCS log、三次波形、自动比对结果
后端结果 Innovus 后端网表、DEF、GDS、主要 log
物理验证 DRC/LVS runset、报告、关键截图
时序签核 SPEF、PrimeTime reports、PrimeTime SDF
总结材料 PPA 汇总、失败原因、修改记录和最终结论

但注意不要把个人账号路径、license 信息、密钥或无关生成文件放进最终提交，工程归档更重要的是可复现的脚本、原始报告和清晰的文件版本。
