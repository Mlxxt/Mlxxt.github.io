数字IC课设工具链（二） | 设计流程总览

发表于2026-06-02|DigitalICTools
|总字数:3.4k|阅读时长:11分钟|浏览量:

这篇文章按我实际接触工具的顺序来写。它不是某个具体电路的设计报告，而是把一套通用数字 ASIC 流程拆开来看：每一步为什么存在，它接住了上一步什么结果，又把什么交给下一步。

0. 环境准备：先让所有工具说同一种话

在真正写 RTL 和跑仿真之前，第一件事是把服务器、VNC、环境变量和工艺库路径准备好。数字集成电路工具链依赖的东西很多：EDA 工具版本、license、标准单元逻辑库、LEF 物理库、Calibre rule deck、StarRC 工艺文件、PrimeTime 时序库等。

环境不统一时，后面的问题常常不是设计错了，而是工具找不到库、读错版本或图形界面打不开。所以环境准备的目标不是“把某个命令跑起来”这么简单，而是保证所有工具使用同一套工艺、库和版本语境。

这一阶段真正通用的要求是：

项目 说明
工具版本 VCS、DC、Innovus、Virtuoso、Calibre、PrimeTime 等版本要与脚本和库兼容
环境变量 工具路径、license、库路径、rule deck 路径要能被脚本找到
图形环境 Verdi、Innovus GUI、Virtuoso、Calibre GUI 需要可正常显示
工艺数据 逻辑库、物理库、SPICE 网表、映射文件和寄生参数文件要来自同一套工艺

1. RTL 行为仿真：先证明代码本身是对的

RTL 仿真是整条流程的第一道门。这个阶段还没有标准单元、没有真实线延时、没有版图，只检查 RTL 在 testbench 激励下是否符合规格。

一个通用的仿真工作区通常需要包含：

内容 作用
RTL 源码 被验证的设计
testbench 产生激励、复位、时钟和自动比较
filelist 固定编译文件列表
Makefile 或脚本 固定仿真命令，减少手工输入错误
波形输出 供 Verdi 或其他波形工具调试

我最建议重视的是 testbench，而不是只打开 Verdi 看波形。比较好的 testbench 应该能自动计算参考结果，自动考虑固定 latency，并在输出不一致时直接报错。Verdi 主要用于失败后的定位，而不是唯一的判定标准。

这一步能优化的对象主要在 RTL 和 testbench：

对象 可以改什么
RTL 拆长组合逻辑、补全同步复位、规范状态机、避免隐式 latch
testbench 增加边界测试、随机测试、reset 场景、协议边界和 scoreboard
仿真脚本 用 filelist 和 Makefile 固定编译顺序，减少路径和顺序错误

2. Design Compiler 综合：把行为描述变成标准单元网表

RTL 仿真通过只能说明“设计意图”对了。真正进入 ASIC 流程后，需要用 Design Compiler 把 RTL 转成由标准单元组成的门级网表。

DC 阶段的核心输入是 RTL、标准单元逻辑库和 SDC 约束。输出不只是一个 .v 网表，还包括 .sdf、.sdc、.svf、.ddc 以及 timing、area、power、QoR 报告。

一个通用的综合工作区可以按角色组织：

内容 作用
RTL 输入 待综合的设计源码
Tcl 脚本 读库、读 RTL、设置顶层、综合、输出报告
SDC 约束 描述时钟、输入输出延时、不确定度和例外路径
输出目录 保存网表、SDF、SVF、报告和日志

这里最需要按自己的设计修改的是顶层模块、RTL 文件列表和 SDC。SDC 决定工具按什么时钟、输入输出延时和不确定度去优化。如果约束漏了，报告好看也不可信；如果约束过于宽松，后续物理实现也可能暴露问题。

DC 的报告里我最先看 timing report。若 slack 为负，说明综合阶段已经达不到时序目标。这个时候不能靠放松时钟周期、漏约束同步输入或删掉 input delay 来“变绿”，而要回到设计结构上看是不是组合路径太长、流水线不够、位宽过大或约束写错。

DC 阶段的优化比较直接：

目标 常见修改位置
时序更好 RTL 流水线、组合逻辑拆分、约束、驱动单元选择
面积更小 资源复用、位宽收敛、减少冗余逻辑、合理限制高性能单元
功耗更低 减少无效翻转、降低扇出、避免过强驱动、优化时钟相关逻辑

3. Formality 前端验证：证明综合没有改坏逻辑

综合工具会做大量优化，门级网表看起来可能已经不像原来的 RTL。Formality 的作用就是用形式方法证明 RTL 和 DC 网表逻辑等价。

这一阶段我认为最重要的是分清 reference 和 implementation。前端 Formality 一般把 RTL 作为 reference design，把 DC 生成的门级网表作为 implementation design。SVF 文件也很重要，它记录了综合过程中的一些转换信息，能帮助 Formality 匹配优化前后的点。

Formality 通过后，我对 DC 网表的信任就不仅来自随机仿真，而是来自形式等价验证。若它失败，先不要马上怀疑 RTL，一般应先检查库、顶层名、端口名、SVF、reference/implementation 是否放反。

4. 综合后门级前仿：门级网表加延时之后再跑一次

前仿使用 DC 输出的门级网表和 DC SDF，再加上标准单元 Verilog 模型。它回答的问题是：综合之后的门级电路，在标准单元延时加入后，是否还能表现出和 RTL 一样的顶层功能。

这一阶段真正不能混淆的是文件来源：

文件 应来自哪里 用途
门级网表 DC 输出 被仿真的实现
SDF DC 输出 标准单元延时反标
标准单元模型 工艺或单元库提供 让仿真器理解门级单元行为
testbench 与 RTL 仿真保持同一套验证逻辑 对比顶层功能

testbench 中的 $sdf_annotate 很关键：

u_dut 必须是 testbench 中被测模块的实例名。如果实例名不对，SDF 可能没有真正反标进去，仿真结论就不可靠。

前仿失败时，我会优先检查三个点：SDF 是否成功 annotation，标准单元模型是否加入 filelist，scoreboard 的 latency 是否仍然对齐。

5. Innovus APR：从逻辑网表进入物理世界

Innovus 是我在流程中感到最“后端”的一步。它不再只关心逻辑表达，而是要把门级网表放到一个实际版图区域里，完成 floorplan、power plan、placement、CTS、routing、filler 和导出。

一个通用的 Innovus 工作区通常需要分清：

内容 作用
综合后网表和 SDC 后端实现的逻辑与约束输入
LEF 和物理库 描述标准单元尺寸、pin、金属层等物理信息
MMMC 配置 描述 mode、corner、library set、RC corner 等
工作数据库和日志 保存 GUI/脚本操作过程
后端输出 导出后端网表、DEF、GDS 等

我把 Innovus 的步骤理解成下面这条线：

步骤 解决的问题
Import Design 让 Innovus 读入网表、约束、物理库和 MMMC 视图
Floorplan 决定核心区大小、利用率、边界和布局空间
Global Net 把 VDD/VSS 这类全局电源地网络连对
Power Ring/Stripe 给标准单元提供稳定供电网络
Pin Editor 固定 IO pin 的位置和金属层，影响布线质量
Placement 摆放标准单元，形成初步物理位置
Tie Hi/Lo Cell 给常量逻辑提供合法单元连接
CTS 建时钟树，控制 skew、transition 和插入延时
Post-CTS Optimization 修复 CTS 之后出现的 setup/hold 问题
Routing 完成电源、地和信号线布线
Post-Route Optimization 基于布线后的真实情况继续优化时序
Filler 填充空白区域，改善井接触和 DRC
Export 导出 GDS、DEF、后端网表等给后续工具

Innovus 阶段最能优化的是物理实现质量。floorplan、pin 位置、利用率、布线层选择、CTS 参数、电源网络都会影响后续 DRC、LVS、StarRC 和 PrimeTime。这里的优化不再只是改 Verilog，而是改物理约束和版图实现方式。

6. Virtuoso + Calibre：检查版图能不能制造、是不是同一个电路

Calibre 主要做 DRC 和 LVS。Virtuoso 则常作为导入 Verilog/GDS、查看 schematic/layout、调用 Calibre 的平台。

DRC 和 LVS 很容易被混在一起，但它们回答的问题完全不同：

检查 问题 通过说明
DRC 版图几何是否满足工艺规则 版图从制造规则角度基本合法
LVS 版图抽取出的电路是否等于网表 物理版图确实实现了同一个逻辑电路

DRC/LVS 阶段真正不能随意替换的是工艺 rule deck、GDS/layout、schematic/netlist、参考库和层映射。报告、runset 和中间文件可以按项目习惯保存，但要保证后续能追溯使用了哪一版版图、哪一套规则和哪一个网表。

LVS 最容易出系统性问题的是 VDD/VSS 名称、global net、label、大小写和参考库。若报告里出现大量 cell mismatch 或 net mismatch，我会先查这些全局设置，而不是一个单元一个单元地改。

7. Formality 后端验证：确认 Innovus 没有改变逻辑

Innovus 可能插 buffer、tie cell，或者做一些物理相关优化。后端 Formality 的作用是比较 DC 网表和 Innovus 后端网表是否逻辑等价。

这一步和前端 Formality 的对象不同，但思想一样：证明工具转换没有改变逻辑功能。reference design 一般是 DC 网表，implementation design 是 Innovus 输出的后端网表。

如果这一步失败，我会先检查是不是后端网表导出错、标准单元库没读全、tie cell 处理不对，或者 reference/implementation 设置反了。

8. StarRC：把版图里的寄生 RC 提出来

到 Innovus 为止，线延时还不是最精确的 signoff 数据。StarRC 会根据版图和工艺信息提取寄生电阻、电容，生成 SPEF 文件。后面 PrimeTime 会使用 SPEF 做更接近真实物理实现的时序分析。

StarRC 阶段真正重要的是脚本里的顶层名、DEF/GDS 路径、工艺文件、映射文件和 PVT corner 要对应。输出 SPEF 时最好按 corner 区分清楚，避免 PrimeTime 读错寄生数据。

StarRC 本身不直接告诉我“设计好不好”，它提供的是更真实的寄生数据。真正判断这些 RC 对时序影响多大，要到 PrimeTime 里看。

9. PrimeTime：后端时序签核

PrimeTime 是静态时序分析工具。它不靠 testbench 激励，而是根据网表、SDC、时序库和 SPEF 系统性检查所有受约束路径。

PrimeTime 可以沿用综合阶段的 SDC 思路，但并不是所有综合脚本语句都适合后端签核。进入 PrimeTime 前，我会确认后端网表、SPEF、时序库、SDC 和 corner 配置彼此对应。

我看 PrimeTime 报告时的顺序是：

  1. 先看 analysis coverage，确认路径真的被分析到了。
  2. 再看 report constraint，确认 setup、hold、transition、capacitance 等是否违例。
  3. 最后看具体 timing path，记录 startpoint、endpoint、corner、slack 和主要延时来源。

如果 coverage 不完整，即使 slack 好看也不可靠。如果 setup 违例，可能需要回 RTL 加流水线，也可能回 Innovus 优化布局布线；如果 hold 违例，通常更多在后端通过插 buffer、调 CTS 或 hold optimization 解决。

10. 版图后仿：用最终后端延时再验证功能

后仿使用 Innovus 后端网表和 PrimeTime 输出的 SDF。它是从仿真的角度对最终物理实现再做一次功能回归。

这一阶段最重要的是文件不能混用：

文件 应来自哪里
后端网表 Innovus 最终导出
SDF PrimeTime 输出
标准单元模型 与网表使用的单元库匹配
testbench 与前面仿真保持同一套功能检查逻辑

后仿通过并不能替代 PrimeTime，因为 testbench 不可能覆盖所有时序路径；PrimeTime 通过也不能完全替代后仿，因为后仿能暴露 SDF 反标、复位、X 传播和测试平台对齐问题。两者互补。

11. GDSII 交付：不是一个文件，而是一条链路的结果

最后导出的 GDSII 是版图交付文件，但我觉得它不能单独看。只有当前面的 RTL 仿真、DC 综合、Formality、前仿、Innovus、DRC/LVS、StarRC、PrimeTime 和后仿都能解释清楚时，这个 GDS 才是一个可信的结果。

我会把最终交付前的检查理解成：

项目 应该能说明什么
RTL 仿真 功能规格在行为级成立
DC 综合 RTL 能转成标准单元网表，PPA 有报告
前端 Formality RTL 和 DC 网表等价
前仿 DC 网表加延时后功能仍一致
Innovus 网表形成了可导出的物理版图
Calibre DRC/LVS 版图满足工艺规则，并与网表一致
后端 Formality Innovus 网表没有改变逻辑
StarRC 物理寄生参数成功提取
PrimeTime 后端时序在约束下收敛
后仿 最终反标延时后功能仍一致

这也是我觉得这套流程最重要的地方：它让一次 RTL 代码最终经过逻辑、物理和时序三重验证，形成一个完整的 ASIC 设计闭环。

数字IC课设工具链（四） | 报告阅读、调试和优化
跑完一次完整流程之后，我觉得工具链里真正难的地方不是“命令怎么输入”，而是看到报告后知道它意味着什么。很多时候，一个错误并不是当前工具本身的问题，而是上一步文件拿错了、约束漏了、目录路径不对，或者设计本身还没有收敛。 这篇文章整理我理解中的报告阅读顺序、常见问题和优化回退路线。 遇到失败时先问四个问题每当某一步没有通过，我会先按这四个问题检查： 当前工具有没有正常读入文件、库和脚本。 当前阶段使用的网表、SDF、SDC、DEF、GDS、SPEF 是否来自正确阶段。 报告失败的类型是什么：功能不一致、形式不等价、时序违例、DRC、LVS，还是寄生提取失败。 这个问题应该回到哪里修：RTL、testbench、SDC、DC 脚本、Innovus 设置、Calibre runset，还是 PrimeTime 脚本。 这个顺序很重要。比如后仿失败时，直接改 RTL 不一定对；可能只是 SDF 没反标到正确实例。LVS 大面积不匹配时，也不一定是几百个 cell 都错了，可能只是 VDD/VSS label 或 reference library 设置错了。 DC 报告：先看...
