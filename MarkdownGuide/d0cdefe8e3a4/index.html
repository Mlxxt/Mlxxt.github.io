Markdown食用指北（七） | 兼容性、排错与写作规范

发表于2026-01-15|MarkdownGuide
|总字数:3.8k|阅读时长:11分钟|浏览量:

本章是整个系列的收尾：建立兼容性意识，形成稳定的排错顺序，并把前六章压缩成一份可以长期查阅的规范与速查表。

真正熟练使用 Markdown，不是记住所有扩展语法，而是能写出清楚的源码，知道目标平台支持什么，并在渲染异常时快速定位原因。

1. 为什么会出现兼容性差异

Markdown 最初追求简单，但不同工具为了满足自己的场景，逐渐增加了不同功能。最终结果是：核心语法相近，扩展能力不同。

一份 Markdown 文档通常经过：

任何一层变化都可能影响结果：

  • 解析器决定语法是否被识别。
  • 插件决定公式、图表和提示框是否可用。
  • 主题决定标题、表格和代码的样式。
  • 浏览器和字体决定部分字符的外观。

所以“编辑器里正常”只能证明编辑器自己的预览正常，不能证明网站构建后也正常。

2. 常见 Markdown 环境

2.1 CommonMark

CommonMark 尝试为 Markdown 核心语法提供更明确的规范和测试。它适合作为理解基础解析规则的参考。

2.2 GitHub Flavored Markdown

GFM 基于 CommonMark，并增加表格、任务列表、删除线和扩展自动链接等功能。GitHub 仓库中的 README、Issue 和 Pull Request 都会受到平台规则影响。

2.3 静态站点生成器

Hexo、Hugo、Jekyll、VuePress、VitePress 等工具会选择不同解析器、插件和主题。即使两者都声称支持 GFM，数学公式、标题锚点、HTML 和代码高亮也可能不同。

2.4 笔记软件与编辑器

Obsidian、Typora、Visual Studio Code 预览等工具可能增加内部链接、嵌入、标注或专用语法。这些内容导出到博客时未必继续有效。

3. 兼容性分层表

下面是实用而不是绝对的分类，最终仍以目标平台测试为准。

功能 通常兼容性 备注
标题、段落 高 井号标题最稳妥
粗体、斜体 高 边界空格可能影响解析
有序、无序列表 高 复杂嵌套依赖正确缩进
引用 高 多段内容注意每行标记
链接、图片 高 路径规则受部署环境影响
行内代码、围栏代码块 高 高亮语言和样式不统一
分隔线 高 注意与 Setext 标题歧义
删除线 中高 常见扩展
表格 中高 不适合复杂合并单元格
任务列表 中高 是否可交互取决于平台
自动链接 中 裸 URL 识别规则不同
脚注 中 标识和回跳样式不同

Mermaid 低到中 依赖插件与版本
提示框、标签页 低 常为主题专用语法

4. 选择语法的优先级

面对多种写法时，可以按下面的顺序选择：

  1. 能用核心 Markdown 清楚表达，就用核心语法。
  2. 核心语法表达明显困难，再考虑常见扩展。
  3. 只有目标网站明确支持，才使用平台专用语法。
  4. 关键信息始终准备可读的降级形式。

5. 建立最小复现

遇到渲染问题时，不要立即修改整篇文章。先复制出最小片段：

然后逐步加入：

  • 原来的缩进。
  • 原来的链接。
  • 原来的代码块。
  • 原来的 HTML。
  • 原来的前后段落。

当某一步加入后问题再次出现，就找到了最接近原因的变化。

最小复现可以区分：

  • 语法本身错误。
  • 与相邻结构发生冲突。
  • 解析器不支持。
  • 主题样式问题。
  • 构建配置问题。

6. 从错误表现反推原因

6.1 后半篇全部变成代码

最常见原因：

  • 代码围栏没有关闭。
  • 关闭围栏字符数量或类型不匹配。
  • 围栏被错误缩进进列表或引用。

6.2 列表突然中断

最常见原因：

  • 列表项后续段落没有缩进。
  • 嵌套层级缩进不一致。
  • 中间插入了未缩进的代码块。
  • 混用了 Tab 和空格。

6.3 标题没有进入目录

最常见原因：

  • 井号后没有空格。
  • 标题位于代码块中。
  • 标题级别超出目录配置范围。
  • 主题关闭了该级别。
  • 标题被 HTML 或插件结构包围。

6.4 示例标题进入目录

最常见原因：

  • 为了展示效果，真的写了标题。
  • 示例没有放入代码围栏。
  • 站点使用了不正确的纯文本扫描逻辑。

正常的 Markdown 目录应根据解析后的标题节点生成，不应扫描代码块中的井号。若代码块内标题仍进入目录，需要检查站点目录插件。

6.5 图片本地显示、线上失效

最常见原因：

  • 大小写不一致。
  • 图片没有加入发布资源。
  • 使用了本机绝对路径。
  • 根路径受站点子目录影响。
  • 构建后资源目录发生变化。

6.6 表格错列

最常见原因：

  • 某一行单元格数量不同。
  • 内容中的竖线没有转义。
  • 分隔行缺失。
  • 单元格中放入了不受支持的块级内容。

6.7 Front Matter 显示在正文

最常见原因：

  • 文件开头存在空白或其他字符。
  • 开始或结束的 --- 缺失。
  • YAML 语法错误导致站点未识别。
  • 文件编码包含异常字符。

7. 逐层排错法

按照下面的顺序排查，效率通常最高。

7.1 源码层

  • 符号是否为英文半角。
  • 括号、强调符号和代码围栏是否配对。
  • 空行和缩进是否正确。
  • 文件编码是否为 UTF-8。

7.2 解析器层

  • 目标语法是否受支持。
  • 插件是否启用。
  • 本地与生产环境版本是否一致。
  • 是否存在平台专用写法。

7.3 路径与资源层

  • 相对路径计算是否正确。
  • 文件是否存在。
  • 大小写是否一致。
  • 构建后 URL 是否变化。

7.4 主题样式层

  • 内容是否已经生成，只是颜色不可见。
  • 表格或代码是否溢出容器。
  • 深色模式是否影响对比度。
  • CSS 是否隐藏某级标题。

7.5 构建与缓存层

  • 构建是否真正成功。
  • 当前查看的是否是最新产物。
  • 浏览器、CDN 或站点是否缓存旧页面。
  • 构建日志是否有警告。

8. 文件编码与换行符

8.1 使用 UTF-8

UTF-8 是中文 Markdown 最稳妥的编码选择。编码错误可能表现为：

  • 中文乱码。
  • Front Matter 无法识别。
  • 构建工具报非法字符。
  • 标点与链接解析异常。

8.2 换行符

Windows 常使用 CRLF，Linux 常使用 LF。现代工具通常都能处理，但团队项目应遵循仓库已有约定，避免因为整文件换行变化产生巨大差异。

8.3 文件末尾换行

文本文件通常建议保留末尾换行。它有助于命令行工具、版本控制和文件拼接保持一致。

9. Markdown 源码风格规范

下面是一套适合教程项目的基础规范。

9.1 标题

  • 井号后保留一个空格。
  • 标题前后留空行。
  • 层级不跳跃。
  • 博客正文从二级标题开始。
  • 只有真实章节使用二、三级标题。
  • 示例标题放进代码块。

9.2 段落

  • 段落之间一个空行。
  • 不连续堆积空行控制间距。
  • 不用空格手工对齐普通正文。
  • 只有确有需要时使用硬换行。

9.3 列表

  • 无序列表统一使用减号。
  • 标记后保留一个空格。
  • 嵌套统一使用四个空格。
  • 同一列表保持紧凑或宽松风格一致。
  • 步骤使用有序列表，并列项使用无序列表。

9.4 代码

  • 文件名、命令和标识符使用行内代码。
  • 多行代码使用围栏。
  • 添加准确语言标识。
  • 命令与输出分开。
  • 不在可复制代码中混入提示符和教学标记。

9.5 链接与图片

  • 使用描述性链接文字。
  • 项目内部优先使用相对路径。
  • 路径大小写与文件完全一致。
  • 图片写有效替代文字。
  • 不引用无权使用或不稳定的外部图片。

9.6 扩展语法

  • 使用前确认目标网站支持。
  • 为关键信息准备兼容降级写法。
  • 不把敏感信息放进 HTML 注释。
  • 不为了装饰引入不必要的平台依赖。

10. 自动检查工具

人工阅读不可替代，但自动工具能发现重复的格式问题。

常见检查方向：

  • 标题跳级。
  • 行尾空格。
  • 列表缩进。
  • 围栏代码块语言标识。
  • 重复标题。
  • 裸 URL。
  • 无替代文字的图片。
  • 失效链接。

项目可能使用 markdownlint、链接检查器或站点构建命令。具体规则应以仓库配置为准，不要把个人偏好强加到已有项目。

10.1 自动格式化要谨慎

格式化工具可能一次修改大量空格、换行和表格对齐。使用前：

  1. 确认规则符合项目风格。
  2. 在少量文件上测试。
  3. 阅读修改差异。
  4. 避免把无关格式变化混入内容修改。

11. 内容质量检查

语法正确的文章也可能不好学。检查：

  • 开头是否说明适用读者。
  • 是否定义第一次出现的术语。
  • 是否先讲前置概念再给复杂步骤。
  • 示例是否能够独立理解。
  • 是否说明成功结果。
  • 是否包含常见错误。
  • 是否有读者可以亲手完成的练习。
  • 是否避免无依据的夸张结论。
  • 是否区分事实、建议和个人偏好。

“尽可能详细”不等于重复。每一段应该至少承担解释、示例、提醒、验证或过渡中的一种作用。

12. 教程截图检查

Markdown 教程通常不需要大量截图，因为源码本身就是最准确的示例。真正需要截图时检查：

  • 截图是否展示了文字无法说明的界面状态。
  • 图片是否裁掉无关区域。
  • 字体是否在移动端仍可辨认。
  • 是否遮挡账号、路径、通知和隐私信息。
  • 是否有替代文字和图注。
  • 软件升级后截图是否仍与正文一致。

能用代码块和渲染结果说明的内容，优先不用截图。

13. 发布前最终清单

13.1 结构

  • Front Matter 正确闭合。
  • 正文没有重复文章标题。
  • 二、三级标题形成清楚目录。
  • 示例标题全部在代码块中。
  • 没有无意义的标题跳级。

13.2 语法

  • 强调符号成对。
  • 代码围栏成对。
  • 列表缩进一致。
  • 表格列数一致。
  • 特殊符号已正确转义。

13.3 内容

  • 目标读者明确。
  • 示例准确且可复制。
  • 步骤包含验证结果。
  • 常见错误有解决方法。
  • 结尾有小结或下一步。

13.4 资源

  • 链接可访问。
  • 相对路径正确。
  • 文件名大小写一致。
  • 图片已发布。
  • 图片替代文字有效。

13.5 平台

  • 自动目录正常。
  • 扩展语法在真实网站可用。
  • 移动端没有严重溢出。
  • 深色模式可读。
  • 构建没有错误。

13.6 安全

  • 没有密钥、令牌和密码。
  • 没有个人或内部地址。
  • 没有真实用户数据。
  • 截图已经脱敏。
  • 引用和图片来源合规。

18. 系列总结

完成七章后，你应该已经能够：

  • 使用核心 Markdown 编写结构清楚的文章。
  • 组合段落、列表、引用和代码。
  • 正确处理链接、图片、路径、锚点和表格。
  • 编写可复制、可验证的技术教程。
  • 谨慎使用脚注、公式、图表、HTML 和提示框。
  • 设计不污染自动目录的长文标题结构。
  • 处理 Front Matter、系列导航和博客资源。
  • 根据错误表现定位围栏、缩进、路径和平台兼容问题。

Markdown 的符号很少，真正值得长期练习的是结构意识：让源码便于维护，让目录便于导航，让示例便于复制，让读者知道自己做对了什么。
