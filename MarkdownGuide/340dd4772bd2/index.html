Markdown食用指北（五） | 扩展语法与 HTML

发表于2025-12-27|MarkdownGuide
|总字数:3k|阅读时长:9分钟|浏览量:

Markdown 的核心语法很小，但现代平台通常会增加表格、任务列表、脚注、提示框、数学公式和图表等能力。这些功能很好用，代价是兼容性下降：同一份源码在不同网站上可能出现不同结果。

本章的重点不是让你记住所有扩展，而是学会判断“哪些语法可以放心使用，哪些必须先确认平台支持”。

1. 核心语法、扩展语法与主题功能

可以把 Markdown 能力分成三层。

1.1 核心语法

跨平台兼容性通常较好：

  • 标题
  • 段落
  • 强调
  • 列表
  • 引用
  • 链接
  • 图片
  • 行内代码
  • 代码块
  • 分隔线

1.2 常见扩展

许多现代平台支持，但仍应预览：

  • 删除线
  • 表格
  • 任务列表
  • 自动链接
  • 脚注

1.3 平台或插件功能

是否可用完全取决于站点配置：

  • 提示框
  • 数学公式
  • Mermaid 图表
  • Emoji 短代码
  • 高亮、上标、下标
  • 折叠内容
  • 标签页
  • 自定义容器
  • 内嵌视频

使用原则是：核心内容不应只依赖平台专用效果才能被理解。

2. GitHub Flavored Markdown

GitHub Flavored Markdown 常缩写为 GFM。它在 CommonMark 基础上增加了若干常见扩展，例如表格、删除线、任务列表和更丰富的自动链接。

“某编辑器支持 Markdown”不等于“它完整支持 GFM”。博客系统可能使用其他解析器，只选择性开启其中一部分能力。

2.1 删除线

适合表示内容被修正或废弃。不要用删除线堆积整段历史修改，正式文档应直接更新正文，并在变更记录中说明。

2.2 任务列表

任务框在博客里通常只是视觉元素，不会保存点击状态。它适合展示进度，不适合真正的多人任务管理。

2.3 表格

复杂表格、合并单元格和多行内容通常需要 HTML，或者改用更适合的结构。

3.2 脚注的兼容性

脚注不是所有 Markdown 环境都支持。若平台不支持，源码中的标识可能直接显示出来。

替代方案：

  • 在相关段落后用括号补充。
  • 增加“参考资料”小节。
  • 使用有序列表列出来源。

不要把关键操作步骤藏进脚注。移动设备上的脚注跳转也可能增加阅读负担。

4.2 主题自定义容器

4.3 提示级别要有区别

  • 说明：补充背景，不影响任务完成。
  • 提示：可以提高效率。
  • 注意：忽略后容易出错。
  • 警告：可能造成数据损失、安全问题或不可逆影响。

如果每段都是警告，读者最终会忽略所有警告。

5. 折叠内容

纯 Markdown 没有统一折叠语法。允许 HTML 时，可以使用 details 和 summary：

5.1 Markdown 是否能在 HTML 块中继续解析

不同解析器处理方式不同。有的平台会继续解析 details 内的 Markdown，有的平台会把它当作原始 HTML 文本。

为了提高兼容性：

  • 在开始标签、内容和结束标签之间保留空行。
  • 不在折叠区域放置完成任务所必需的步骤。
  • 在目标网站测试列表、代码块和图片。

5.2 适合折叠的内容

  • 很长但非必要的日志。
  • 参考答案。
  • 额外背景。
  • 完整配置示例。

不适合折叠：

  • 安全警告。
  • 必做步骤。
  • 关键错误信息。
  • 文章的主要结论。

6.3 HTML 的风险

  • 平台可能过滤标签或属性。
  • CSS 样式在不同主题中不同。
  • 迁移平台时可能失效。
  • 不安全的 HTML 可能带来脚本注入风险。
  • HTML 与 Markdown 混排的空行规则可能不同。

只在 Markdown 本身无法清楚表达时使用 HTML。

8.1 使用公式前检查

  • 网站使用哪一个数学渲染器。
  • 行内和块级定界符是什么。
  • 是否需要在 Front Matter 中启用。
  • 反斜杠是否被 Markdown 提前转义。
  • 公式编号和引用是否支持。

8.2 简单内容不必强行使用公式

像 x + y = 10 这样的短表达式可以直接用行内代码或普通文本。只有真正需要分数、矩阵、上下标和数学排版时，公式渲染才更有价值。

  • 时序图
  • 状态图
  • 类图
  • 简单项目计划

注意：

  • Mermaid 语法和版本会变化。
  • 复杂图在手机上可能难以阅读。
  • 中文字体和深色主题可能影响显示。

图表是辅助，不应成为理解文章的唯一途径。

如果网站已经自动生成目录，正文不要再插入第二套目录。真正需要控制的是：

  • 标题层级是否连续。
  • 标题是否简短明确。

14. 内容迁移时的降级策略

当目标平台不支持某项扩展时，可以这样降级：

扩展功能 兼容替代
提示框 块引用加粗体标签
脚注 参考资料小节或括号说明
折叠内容 普通小节
数学公式 图片或纯文本表达式
Mermaid 图片加文字说明
定义列表 粗体术语加普通列表
自定义标签页 多个三级标题
复杂表格 多个列表或小节

优雅降级的目标不是保留一模一样的视觉效果，而是保留信息。

15. 判断能否使用扩展语法

使用一项新语法前，回答下面的问题：

  1. 当前网站的解析器或主题明确支持吗？
  2. 本地预览与生产网站使用同一套解析器吗？
  3. 不支持时，读者还能理解核心内容吗？
  4. 文章未来是否可能迁移到其他平台？
  5. 这项扩展真的比核心语法更清楚吗？
  6. 移动端和深色模式下是否可读？

只有“看起来更酷”通常不是引入平台依赖的充分理由。

16. 本章小结

  • 核心 Markdown 最适合长期维护和跨平台迁移。
  • GFM 增加了表格、任务列表、删除线和自动链接等常见能力。
  • 脚注、警告框、数学公式、Mermaid 和 Emoji 短代码都需要确认平台支持。
  • HTML 可以补充 Markdown，但会增加样式、安全和迁移成本。
  • HTML 注释不是秘密存储位置。
  • 扩展语法失效时应尽量保留信息，而不是只追求视觉效果。
